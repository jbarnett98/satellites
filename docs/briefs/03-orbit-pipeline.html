The orbit pipeline: fetch, validate, snapshot, archive — on a schedule

The platform now has its data supply. Every hour a scheduled task on your PC asks the pipeline to run; the pipeline decides, dataset by dataset, whether CelesTrak's rules allow a download, fetches what it may, validates every element set with the reference SGP4 implementation, joins the satellite catalogue, writes the snapshot the site will load, and files one gzipped copy of everything per day into an archive that starts today. The first run brought in 19,248 objects.

What we just completed

  • A CelesTrak client that cannot misbehave. It remembers, per dataset, when it last asked, when it last succeeded and when it may next ask; it never polls faster than hourly; it treats a 403 as information ("you're ahead of their update") rather than an error; it halts and backs off for six hours on a server error; and it fails loudly if a URL ever redirects or 404s. Six GP groups are tracked: active (16,564 objects), stations, last-30-days, and the Fengyun-1C, Iridium 33 and Cosmos 2251 debris clouds. SATCAT is checked through its directory listing and downloaded only when its modification time changes.
  • Validation with the reference propagator. The sgp4 package — the same algorithm satellite.js runs in the browser — initialises every set and propagates all of them at once at three times. On the first run: 19,527 records in, 278 cross-group duplicates resolved to the newest epoch, one decayed object rejected, 55 flagged stale, 19,248 accepted.
  • The snapshot format the site will load. Column-oriented JSON: 17 OMM fields carried verbatim (so the browser can hand each object straight to satellite.js), 8 derived fields (period, semi-major axis, apogee, perigee, regime, epoch age, flags, groups), 7 SATCAT fields (type, status, owner, launch date and site, decay date, radar cross-section). A manifest records the version, counts, validation summary and provenance. 5.0 MB raw, 1.09 MB gzipped.
  • Storage with the production shape. Raw responses kept 7 days; a permanent daily archive; the latest snapshot served with the exact cache semantics object storage will use later (manifest revalidated, versioned files immutable).
  • Scheduling. A PowerShell script registers, inspects or removes the hourly task. Registered with your approval and exercised once by hand: exit 0, gates held, nothing fetched.
  • Probing first, then building. Before writing the client we made one tiny request (the ISS by catalogue number) to see what CelesTrak actually sends back — no Last-Modified, no ETag — which changed the design from conditional requests to time-based pacing. That single request cost one window on a dataset we never use.
Working principles honoured

No database, no queue, no scheduler framework: one Python entry point, one state file, one JSON manifest, and the operating system's own scheduler. The browser never talks to CelesTrak. Every source is credited in the manifest.

Under the hood: fetch discipline

The whole client exists to satisfy one sentence of CelesTrak's policy: only download data once per update, where GP updates land every two hours and a second request in the same window is answered 403. Two facts from the probe shaped the design: gp.php sends no Last-Modified or ETag, so a request cannot be made conditional; and the SATCAT directory listing (satcat/jsonDir.php) does report a modification time, so SATCAT can be polled cheaply.

Locking onto their cadence. CelesTrak updates at some fixed two-hourly phase we cannot see. Our first request in a window succeeds at some offset δ after their update. If we then request every two hours at the same minute, δ never changes and we never see a 403. If we happen to have asked just before an update (δ ≈ negative), the request gets 403, the next hourly run succeeds, and δ becomes roughly an hour — stable from then on. Expect at most one or two 403s in the pipeline's whole life, both harmless.

What the state file holds. For each of the seven datasets: last attempt, last success, last HTTP status, path of the newest raw file, SHA-256 of its body (so "downloaded but identical" is detectable), next-allowed time, and a count of consecutive 403s; plus a global back-off time and the SATCAT directory's last-checked time and modification stamp. It is plain JSON in data/orbits/state.json; deleting it resets the discipline, which is the one way to make the client misbehave — hence the comment inside it.

Under the hood: validation

Nothing reaches the snapshot without passing three layers, each catching something the previous one cannot:

  1. Shape and range. Thirteen required fields present and numeric; 0 ≤ e < 1, 0° ≤ i ≤ 180°, 0 < n ≤ 20 rev/day; the epoch parses. Then de-duplication: the six groups overlap (the ISS is in active and stations), and for each catalogue number the newest epoch wins — 278 removed on the first run.
  2. Initialisation. The sgp4 package's OMM loader builds a propagator record from the exact field names CelesTrak sends. Anything it refuses is rejected with the exception's name as the reason.
  3. Propagation. All accepted records are propagated together (vectorised, milliseconds for 19k) at three moments: each set's own epoch, now, and now plus one day. SGP4's own error codes then speak: 6 means the object has decayed (rejected — one on the first run), 5 means sub-orbital, 1–4 are numerical pathologies a range check cannot see.

Sets older than 14 days are kept but flagged stale (55 on the first run) so the site can warn; sets older than 60 days are dropped — the propagator would place them kilometres wrong and CelesTrak would not still be listing an active object that old without a reason. The validator also computes, from the elements alone, each object's period, semi-major axis, apogee and perigee altitude, and a coarse regime — LEO / MEO / GEO / HEO / HIGH — so the site's first filters need no further maths. The first snapshot: 18,422 LEO, 552 GEO, 194 MEO, 46 HEO, 34 above GEO.

The synthetic tests run before the first real fetch are in the log of this session rather than in the repo; a proper test file is a natural addition when the pipeline gets its first regression.

Under the hood: snapshot and storage

The snapshot file is column-oriented: a columns block describing each of 32 fields, and a data block holding one array per field, all of length 19,248, sorted by catalogue number. The 17 OMM fields are carried verbatim — the epoch as CelesTrak's ISO string, the numbers as the same doubles — so the browser can rebuild the OMM record for any object and pass it to satellite.js unchanged. Alongside ride the derived orbit numbers, the flags, the groups an object appeared in, and the SATCAT metadata: type (16,564 payloads, 2,665 debris, 12 rocket bodies, 7 unknown), operational status, owner, launch date and site, decay date, radar cross-section class.

The manifest is what the site reads first: the current version, the snapshot filename, its size, the counts above, the validation summary, and provenance for every input (which raw file, fetched when, SATCAT's upstream modification time). The manifest is served with Cache-Control: no-cache — always revalidated — and the versioned snapshot with a one-year immutable lifetime, because its name changes whenever its content does. The newest two versions are kept so a page that already read the manifest can still fetch its file during a rebuild. This is precisely the contract object storage will honour later; today a 40-line Vite middleware honours it on localhost.

Storage tiers. Raw responses are the ground truth and are kept for seven days, so a bad snapshot can be rebuilt from exactly what was received. The archive keeps one gzipped copy per dataset per UTC day — overwritten within the day, final at midnight — roughly 2.8 MB a day, a gigabyte a year, and the raw material for every "how did this orbit change" feature in the plan. Nothing under data/ is in git.

Size. 5.0 MB raw, 1.09 MB gzipped, for 19,248 objects with full metadata. The browser will need only part of it per object at first; splitting the OMM columns from the metadata columns is a two-line change in the builder if the first load ever needs to be lighter.

Immediate next avenues

A

Satellites on the globe

The browser reads the manifest and snapshot, a Web Worker builds satellite.js records from the verbatim OMM columns and propagates all 19k about once a second, the main thread extrapolates and draws one point cloud in world; click → orbit path, ground track, detail panel from the metadata columns. The whole plan's centrepiece, and every input for it now exists.

Trade-off: none worth naming — this is the natural next stage.

B

The full catalogue via Space-Track

You register an account (I can't); the pipeline gains a second client with Space-Track's own limits (30 requests/min, 300/hour) pulling the complete GP set (~35k) a few times a day; validation and snapshot are unchanged. Turns the debris toggle from "three clouds" into "everything".

Trade-off: Space-Track's user agreement restricts redistribution without an Orbital Data Request — fine while the site is local, a form to file before it is public.

C

Pipeline hardening

A test file with the synthetic cases; a summary e-mail or desktop notification on halts; SupGP (operator ephemerides for Starlink/OneWeb) as a seventh dataset; a "stale snapshot" warning if the archive misses a day.

Trade-off: all small; best folded into whatever stage first needs them.

D

First deployment

GitHub remote, Cloudflare Pages for the site, R2 for data/orbits/latest with the same cache headers; the pipeline gains a one-function uploader.

Trade-off: still publishes a globe with nothing orbiting it unless A comes first.

Open questions and risks

Needs your decision

Rocket bodies and the rest of the debris. CelesTrak publishes no all-objects dataset: today's 19,248 covers every active satellite plus three historic debris clouds, but the other ~16,000 tracked objects — most rocket bodies, most fragments — exist only in Space-Track's catalogue, which needs a free account (yours to create) and, for public redistribution, an Orbital Data Request. Two honest options: build the satellite layer on today's data and add Space-Track later; or register now so the pipeline can start archiving the full catalogue from day one. The archive is the argument for sooner.

  • The PC has to be on. Task Scheduler runs only while the machine is awake; missed hours are simply missed (the next run catches up in one fetch). Migration to a cloud runner is one workflow file when you want it.
  • One window was spent on the probe. The ISS-by-catalogue-number request used that dataset's window; we never use that dataset, so nothing was lost.
  • CelesTrak's update phase is inferred, not known. If they change cadence, the client adapts through 403s rather than breaking, but the log will show it.
  • Epoch strings. The validator tolerates a missing fractional second; if CelesTrak ever changes the timestamp format, sets would be rejected with "unparseable epoch" and the manifest would show it.
  • SATCAT column names are read by name and degrade to blanks if renamed upstream; the log warns.
  • Snapshot weight is 1.09 MB gzipped — acceptable, and splittable.
  • No tests in the repo yet. The validator was exercised with synthetic bad records in this session; the cases are cheap to turn into a test file.

Running it

npm run orbits                  # one run: fetch if allowed, validate, snapshot, archive (13 s first time, 0.3 s when gated)
npm run orbits:status           # what was fetched when, when each dataset may next be asked for, current snapshot
npm run orbits:rebuild          # rebuild the snapshot from the newest raw files without touching CelesTrak
npm run orbits:schedule:status  # the Task Scheduler job: state, last run, next run
npm run orbits:unschedule       # remove the job

Files to know: data/orbits/latest/manifest.json (what the site sees), data/orbits/state.json (the client's memory — don't delete casually), data/logs/orbits.log. In the browser: http://localhost:5173/data/orbits/manifest.json.
