The framework: a globe that keeps real time

The site exists and runs locally. It draws a WGS84 Earth lit by the real Sun, turning under 9,096 real stars, with a clock you can pause, warp and jump, a reference-frame toggle, a layers menu and a status readout. No satellites yet — this stage was about getting every foundation they will sit on right.

What we just completed

Session zero plus the visual foundation, in one pass:

  • Toolchain. Installed Node.js 24.19 LTS (winget). Python 3.14 was already present via the py launcher. Git was present.
  • Assets. Downloaded NASA's Blue Marble (Dec 2004, with topography and bathymetry, 5400×2700) and Black Marble 2016 night lights (3600×1800), both public domain, and the Yale Bright Star Catalogue (BSC5, 9,110 records) into data/raw/.
  • First pipeline script. build_stars.py parses BSC5's fixed-width records (standard library only), drops the 14 entries with no position, and writes a 287 KB column-oriented stars.json. Sirius comes out brightest at V = −1.46, which is the right answer.
  • The web app. Svelte 5 + Vite 8 + TypeScript 5.9 + Three.js r186. Custom shaders for the Earth, the atmosphere and the stars; no Three.js lights anywhere — all lighting derives from one computed sun vector.
  • Astronomy. Julian date, Greenwich Mean Sidereal Time (Vallado's polynomial, the same one satellite.js uses, so the Earth and the future satellites will agree on where Greenwich is), and the Astronomical Almanac low-precision Sun.
  • UI. Wordmark and live UTC clock with a LIVE / SIM / PAUSED badge, inertial ↔ Earth-fixed toggle, layers panel (day/night, city lights, atmosphere, stars, graticule), time controls (now, pause, rates, jump), status bar (camera lat/lon/altitude, sub-solar point, GMST, fps, star count, data credits).
  • Verification. svelte-check: 0 errors. Production build: 160 KB gzipped. Sub-solar point at 16:06 UTC on 11 Sep came out at 4.4° N, 62.5° W — the right latitude for the date and the right longitude for the hour. WebGL is running on the RTX 5070 via ANGLE/D3D11.
Working principles honoured

No server, no database, no Docker, no framework beyond Svelte + Three. One Python script with zero dependencies. Every asset credited in the status bar. Desktop-only layout, as agreed.

The dependency direction is strict and worth keeping: ui/ → state/ → globe/ → astro/. The astronomy modules import nothing but Three's Vector3; the globe modules never import Svelte; the UI never touches Three directly except in GlobeCanvas, which is the one deliberate bridge. When the satellite layer arrives it slots into globe/ with a worker beside it, and gets its own state/ module.

Two commands, two outputs

npm run dev starts Vite: it serves index.html, compiles each .svelte/.ts file on demand as the browser requests it, and pushes changes over a websocket. npm run build runs the same compiler over everything once, tree-shakes Three.js down to the parts we import, minifies, and writes web/dist/: one HTML file, one CSS file, one JS file (160 KB gzipped, Three.js included), plus copies of public/. That dist/ folder is the entire deployable site — later, Cloudflare Pages just hosts it.

How the pipeline feeds the site

The pattern that will carry every future dataset is already in place in miniature: a Python script reads a raw upstream file from data/raw/, validates and reshapes it, and writes a compact, column-oriented JSON into web/public/data/, where the site fetches it as a static file. The star file stores ra[], dec[], mag[], bv[] as parallel arrays rather than one object per star — smaller, faster to parse, and the browser copies each array straight into a GPU attribute. The satellite snapshot will use the same shape.

Under the hood: one frame

Everything visible is a pure function of one number, simTime. The browser asks for a new frame roughly 60 times a second, and each time the globe runs the same sequence:

The scene graph and the two frames

Scene units are kilometres and the layout is Earth-centred inertial (ECI), remapped to Three's y-up: scene.x = eci.x, scene.y = eci.z, scene.z = −eci.y. That mapping is right-handed, puts north up, and — not by accident — makes east longitude increase in exactly the direction an equirectangular texture wraps onto Three's sphere, so the Earth needs no texture offset: rotate the mesh by GMST about y and Greenwich lands where it should.

Two groups do all the work. earthGroup holds the Earth mesh, the atmosphere shell and the graticule, is scaled by 6356.752 / 6378.137 in y (so the whole planet is a WGS84 ellipsoid, not a sphere), and rotates by GMST every frame. Its parent, world, is the inertial frame: rotation zero in the inertial view. Switching to Earth-fixed sets world.rotation.y = −GMST, which exactly cancels the Earth's spin — and the camera is rotated by the same delta at that instant so the picture doesn't jump. Satellites will be children of world, because that is the frame their propagator works in.

The stars live in a second scene rendered first, through a camera that copies the main camera's rotation but never its position. They are therefore at infinity regardless of zoom and never touch the depth buffer. The depth buffer is cleared between the two passes, so the Earth always occludes the sky behind it.

Lighting without lights

There are no Three.js light objects. The Sun's direction for the current simTime is computed once per frame (mean longitude, mean anomaly, ecliptic longitude, obliquity — a dozen lines), converted to scene space, and passed to both the Earth and atmosphere shaders as a uniform. The Earth fragment shader computes dot(normal, sun) per pixel: a smoothstep over ±0.10 gives a ~12° twilight band; the day side gets Lambert shading plus a warm push near the terminator, a specular glint where the Blue Marble is blue (oceans), and a blue tint toward the limb; the night side shows a faint 3.5% of the day texture plus Black Marble's city lights tinted sodium-orange. The atmosphere shell is drawn back-face-only with additive blending: because the Earth is drawn first, only the ring of shell outside the planet's disc survives the depth test, and that ring is the glow.

The clock

clock.tick() is called by the globe once per frame. In live mode it copies Date.now(); otherwise it adds real elapsed milliseconds × rate. Jumping to a date sets the time and pauses. Because every displayed quantity is recomputed from simTime each frame, 3,600× time-warp is just a bigger number — nothing else changes.

Immediate next avenues

Four directions are open. They are not mutually exclusive, but each is a coherent stage on its own.

A

The satellite data pipeline

Register on Space-Track (for later), write the CelesTrak fetcher with the correct one-download-per-update discipline (check jsonDir.php, download changed groups once, treat 403 as "wait"), validate every element set with Python's sgp4, join SATCAT metadata, and define the column-oriented snapshot format the browser will load. Start the daily archive.

Trade-off: nothing new appears on screen at the end of this stage, but every later stage depends on it, and the archive clock only starts when it runs. First real Python dependency → uv project.

B

The satellite layer, with a hand-made test set

Build the browser side first: satellite.js in a Web Worker, positions + velocities to a typed array, extrapolation on the main thread, a point cloud in world, orbit path on selection — driven by a small static file of a dozen element sets (ISS, Hubble, a GPS bird, a Starlink) copied in by hand.

Trade-off: the most visible progress, and it lets us design the rendering and picking with real motion — but the test file will go stale within days and A still has to happen before anything is "real time".

C

Globe polish

Convert textures to WebP (and add an 8k option), a specular/ocean mask instead of the blue-minus-red heuristic, a subtle cloud layer, camera fly-to and keyboard shortcuts, a "star brightness" setting, self-hosted fonts.

Trade-off: makes the centrepiece more beautiful now, at the cost of delaying the thing the platform is for. Any item here can also be folded into a later stage.

D

First deployment

Create the public GitHub repo, connect Cloudflare Pages, and put what exists at a real URL. Establishes the deploy path while the site is still simple.

Trade-off: cheap and de-risks hosting early, but publishes a globe with nothing orbiting it. Pairs naturally with A or B as a half-stage.

Open questions and risks

Needs your eyes

Frame rate is unmeasured. The embedded browser pane pauses requestAnimationFrame whenever it isn't actively displayed, so the fps counter read 1–4 there and cannot be trusted. WebGL is confirmed to be on the RTX 5070, and the scene is two 128-segment spheres and 9k points, so I expect a solid 60 — but please open http://localhost:5173 in your own browser and read the "Render" line in the status bar. That number becomes the baseline for the satellite layer.

  • Texture weight. 3.2 MB of JPEG is fine on localhost and acceptable for desktop, but WebP would roughly halve it. Deferred to polish.
  • Fonts from Google. Fine for development; self-host before deployment for privacy and offline use.
  • Star visibility is calibrated by eye in a downscaled capture; the size and alpha curves may want a nudge once you see them at 1:1. A user-facing brightness control is a cheap addition.
  • Ellipsoid normals use the plain model matrix rather than the inverse transpose — a 0.3% error that is invisible, noted for honesty.
  • Atmosphere thickness is tuned for a distant camera; the limb-depth threshold (0.30) is an approximation that softens when you zoom close. A per-frame exact threshold is a small follow-up.
  • Hot reload re-creates the WebGL context. Expected with Vite; harmless in development, but it means the camera resets on every code change. A "remember camera" dev nicety is possible.
  • Star catalogue depth. BSC5 stops around V ≈ 6.5 (naked-eye limit). If a denser sky is ever wanted, the HYG database (120k stars) drops into the same script.
  • Nothing is committed. The repo is initialised on main with a .gitignore that excludes data/, node_modules/ and dist/; textures and stars.json (3.5 MB) would be committed as static assets unless you prefer otherwise.
