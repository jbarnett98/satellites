Preface

Atmospheric Perspective is a browser-based platform for satellite data. Its centrepiece is a three-dimensional globe on which every publicly tracked object in Earth orbit will move in real time, propagated in the browser from fresh orbital element sets; around it sit explorers, dashboards and observer tools built on the same data. The project is deliberately static-first: the browser does the orbital mechanics, a small pipeline refreshes the data on a schedule, and hosting is meant to cost nothing. A previous version of this idea, built on a cloud provider with orchestration and containers added early, taught the lesson that shapes every decision here: add machinery only when a feature demands it.

This journal is written as the work happens. Each part covers one component of the system and follows the same six headings — context, what was built, how it works, decisions and alternatives, measurements, what this enables next — so that the document reads as one process from the first line to the last. Where a component was revised after review, the revision is told inside the same part rather than as a separate chapter, because the revision is part of how the thing came to be.

Part1

The Globe

11 September 2026 · commits 7a3e84d, f16d9b8 · web/src/lib/{astro,globe,state}, web/src/ui, pipeline/ap_pipeline/{textures,sky}

1.1Context

Before any satellite could be drawn, the world it would be drawn into had to exist: a planet with the correct shape, lit by the real Sun for the real time, turning at the right rate under a sky fixed to the stars. Everything a satellite layer will need — a coordinate frame, a clock, a way to turn simulation time into a picture — is decided here, and the cheapest time to decide it correctly is before there are ten thousand moving objects depending on it.

The plan that preceded the build (the "game plan", 11 September 2026) had already fixed the architecture: a Svelte 5 single-page application built with Vite, rendering through Three.js with hand-written shaders, and a Python pipeline that turns raw upstream data into small static files. It had also surfaced one fact that made the static-first design mandatory rather than merely economical: since 26 March 2026 CelesTrak, the public source of orbital element sets, permits one download per dataset per two-hour update window and answers a second with HTTP 403. A site whose browsers fetched element sets directly would fail on its second visitor. The pipeline therefore fetches once and the site serves its own copy — and that same pattern, raw data in, small derived file out, was rehearsed in this part with the sky before it is trusted with the satellites.

The work was done in two sittings on the same day. The first produced a working globe from nothing; Jack reviewed it and asked for four things — slower camera drag, a sharper Earth, a fuller sky "possibly even the centre of the Milky Way, though I like the idea of plotting the stars rather than an image", and the Sun visible in its true position — plus a subtle cloud layer and more descriptive file names. The second sitting delivered those. This part describes the result as one thing, and notes along the way what the first pass did differently and why it changed.

1.2What was built

The toolchain. We installed Node.js 24.19 (for the build tools only; nothing of ours runs on Node in production) and later uv 0.12 for the Python side. Python 3.14 and Git were already present. The web application is Svelte 5.57, Vite 8.3, TypeScript 5.9 and Three.js r186; the production build is a single HTML file, one stylesheet and one 165 KB (gzipped) script, Three.js included.

The repository. A monorepo with three concerns — web/ for the site, pipeline/ for the data work, docs/ for briefs and this journal — plus a git-ignored data/raw/ for downloaded originals. Inside web/src the dependency direction is strict and one-way: user interface → shared state → globe → astronomy. The astronomy modules import nothing but a vector type; the globe modules never import Svelte; the interface never touches Three.js except through one component, GlobeCanvas, which is the deliberate bridge.

The Earth. A WGS84 ellipsoid — equatorial radius 6378.137 km, polar 6356.752 km — textured with NASA's Blue Marble Next Generation (December 2004, with topography and bathymetry) by day and Black Marble 2016 city lights by night. The first pass used NASA's 5400×2700 JPEG directly. On review it was judged too soft, and we went back to the 21,600×10,800 original (30 MB) and had the pipeline resample it to three WebP tiers of 2048, 4096 and 8192 pixels wide; the site paints the 2048 tier within about a second and swaps the 8192 tier in behind it. A custom fragment shader blends day and night across a soft terminator, adds Lambert shading, warms the light near the terminator, glints off water and tints the disc blue toward the limb.

The atmosphere. A shell 4.5% larger than the Earth, drawn back-face only with additive blending. Because the Earth is drawn first, only the ring of shell outside the planet's disc survives the depth test, and that ring is the glow — brightest at the limb, fading outward, dimmer on the night side, warmer near the terminator.

The clouds. Added in the second sitting: NASA's Blue Marble cloud composite as a translucent shell 25 km above the surface, opacity 0.42, lit by the same sun vector as the ground so it shares the terminator. Clouds also darken the ground beneath them by up to 22% and hide up to 80% of the city lights below, which is what makes the shell read as a layer rather than paint. The sheet drifts eastward at 0.25° per simulated hour — an artistic touch, invisible at real speed, documented as non-physical.

The Sun. A billboard sprite placed along the computed sun vector each frame, drawn with a canvas-generated radial gradient whose inner stop is sized so the bright disc subtends the Sun's true 0.53°, inside a soft nine-degree glare. It is drawn in the sky pass, so the Earth occludes it: sunrise and sunset over the limb need no special handling.

The stars. The first pass plotted the Yale Bright Star Catalogue — 9,096 naked-eye stars — as points. It looked sparse. The second pass replaced it with the HYG database (Hipparcos, Yale and Gliese combined): 119,613 stars, each at its J2000 right ascension and declination in the inertial frame, sized and faded by visual magnitude and coloured by its B−V index through a small black-body ramp. Because the stars live in the inertial frame they hold still while the Earth turns beneath them, which is what the sky does.

The Milky Way. Jack's brief was specific: see the galaxy, but plot data rather than paste a photograph. The galaxy, to the eye, is the integrated light of stars too faint to resolve individually, so we reproduced it the same way. The pipeline reads the Tycho-2 catalogue — 2,539,913 stars — sums their light into a sky-brightness map, and the browser drapes that map over the celestial sphere underneath the plotted stars. The band, the dark lanes of the Great Rift and the bulge toward Sagittarius all emerge from the catalogue. The map is 4096×2048 pixels and 202 KB.

Postscript, 12 September. The Milky Way did not survive contact with a full-resolution display. Seen at 1:1 on Jack's monitor the map read as blotches — at the globe's 40° field a 4096-wide map gives 455 texels across the screen, and a seven-texel blur is thirty screen pixels. We regenerated it at 8192×4096 with a five-texel blur; the band's structure appeared, but so did grain, because 2.5 million stars are a sparse sample of the galaxy and at that resolution the grain is the stars themselves. Sharp or smooth, not both, from this catalogue. Jack chose neither over a photograph, and the map, its shader, its slider and its builder were removed (commit 05b5893). The lesson is recorded in Part 3: a star-count map needs Gaia-scale density, not more blur. The plotted stars remain.

Time and frames. A simulation clock that follows the wall clock, or runs at 1× to 3,600× real time, or pauses, or jumps to a chosen date; every visible quantity is recomputed from its single value each frame. Two reference frames, switchable without a visual jump: inertial (the sky holds still, the Earth turns) and Earth-fixed (the Earth holds still, the sky and Sun move).

The interface. A top bar with the wordmark, a live UTC clock and a LIVE / SIM / PAUSED badge, the frame toggle and a Layers button; a layers panel with toggles for day/night shading, city lights, clouds, atmosphere, stars, the Milky Way and a 15° graticule, plus sliders for star brightness and Milky Way intensity; time controls; and a status readout of camera latitude, longitude and altitude, the sub-solar point, sidereal time, frame rate, texture tier and star count, with data credits beneath.

The pipeline. Three Python modules, named for what they do, run from a uv project with two dependencies (NumPy, Pillow): build_earth_textures_from_nasa, build_star_catalog_from_hyg, build_milky_way_glow_from_tycho2. The first pass had a single dependency-free script called build_stars.py; the name was rightly called out as saying nothing, and the restructuring followed.

1.3How it works

Coordinates. Scene units are kilometres. The scene is laid out in the Earth-centred inertial frame — x toward the vernal equinox, z toward the north pole — remapped to Three.js's y-up convention as scene.x = eci.x, scene.y = eci.z, scene.z = −eci.y. The mapping is right-handed, puts north up, and makes east longitude increase in exactly the direction an equirectangular texture wraps onto Three's sphere, so the Earth needs no texture offset: rotating the mesh by Greenwich Mean Sidereal Time about y puts Greenwich where it belongs. GMST is computed from the Julian date with the same polynomial the satellite propagator library uses, so the Earth and the future satellites will agree on where Greenwich is.

The scene graph. Two groups do the work. earthGroup holds the Earth mesh, the cloud shell, the atmosphere shell and the graticule; it is scaled by 6356.752/6378.137 in y so the whole planet is an ellipsoid, and it rotates by GMST every frame. Its parent, world, is the inertial frame, with rotation zero in the inertial view. Switching to the Earth-fixed view sets world's rotation to −GMST, which exactly cancels the Earth's spin, and rotates the camera by the same delta at that instant so the picture is continuous. Satellites will be children of world, because that is the frame their propagator produces.

The sky is a second scene rendered first, through a camera that copies the main camera's rotation but never its position, so the stars are at infinity regardless of zoom and never touch the depth buffer. Its root group carries the Milky Way dome, the star points and the Sun sprite in that draw order, and follows world's rotation so the sky and the Earth stay consistent in both frames. The depth buffer is cleared between the two passes; the Earth therefore always occludes the sky — and the Sun — behind it.

One frame. The browser asks for a frame roughly sixty times a second (240 on Jack's machine). Each time, the globe asks the clock for the simulation time, converts it to a Julian date, computes GMST and the Sun's direction (the Astronomical Almanac's low-precision solar algorithm, accurate to about a hundredth of a degree), poses the two groups, writes the sun vector and camera position into the shader uniforms, renders the sky and then the world, and every 200 ms reports a status object back to the interface. The interface, for its part, pushes changes into the globe through Svelte effects — a frame toggle, a layer switch, a slider — and otherwise leaves it alone.

Lighting without lights. There are no Three.js light objects. Every shader receives the same sun vector and computes dot(normal, sun) per pixel. On the Earth a smoothstep over ±0.10 in that quantity gives a twilight band roughly twelve degrees wide; the day side gets Lambert shading plus a warm push toward the terminator, a specular glint where the Blue Marble is blue, and a blue tint toward the limb; the night side shows 3.5% of the day texture plus the city lights tinted sodium-orange. The cloud shader lights coverage the same way, warms it near the terminator and dims it to blue-grey at night. The Earth shader also samples the cloud map, offset by the same drift, to shadow the ground and dim the lights beneath cloud.

Two loading tiers. The globe loads in two waves. Wave one fetches the 2048-wide day, night and cloud maps, the star binary and the Milky Way map in parallel — about two megabytes — builds every object, and reports ready. Wave two fetches the 8192 day and night maps and the 4096 cloud map, hands them to the shells, and frees the small ones; nothing on screen changes except sharpness. A returning visitor loads all of it from cache.

The pipeline, module by module. Each module reads originals from data/raw/ and writes something small into web/public/. The texture module opens the 233-megapixel Blue Marble (Pillow's decompression-bomb guard has to be switched off), converts to RGB and resamples with a Lanczos filter to each tier, saving WebP at quality 86; the same for Black Marble and, as a single grey channel, the cloud composite. The star module reads the HYG CSV, converts right ascension from hours to degrees, drops the Sun, sorts by magnitude and packs each star into four little-endian 16-bit integers — RA and Dec in hundredths of a degree, magnitude and B−V ×100 — eight bytes a star, a precision of 36 arcseconds, thirty times finer than a screen pixel at the globe's field of view; names for 759 stars go in a sidecar file keyed by row.

The Milky Way module is the one worth describing in full. It reads all twenty Tycho-2 parts (four seconds in Python 3.14), converts each star's Tycho BT and VT magnitudes to Johnson V and B−V with the standard relations, and discards stars brighter than V 8, which are plotted individually and would otherwise be counted twice. Each remaining star contributes a weight of 10−0.4·max(V, 10) — flux, but capped at tenth magnitude, so a single ninth-magnitude star cannot make a blob and the map traces the density of faint stars, which is the classic technique for Tycho-2 all-sky maps and is what the eye actually perceives. Contributions are coloured by B−V through the same black-body ramp the browser uses, binned into a 4096×2048 grid of right ascension and declination, and divided by the cosine of declination so that a pixel near the pole, which covers less sky, is expressed as surface brightness rather than count. The grid is then smoothed with a Gaussian of seven pixels (about 0.6°) by FFT, chosen because it wraps at RA 0° and leaves no seam; the 55th-percentile floor is subtracted so empty sky is black, the result is normalised to the 99.8th percentile and given a gamma of 0.85, and the map is written as WebP.

In the browser the map is decoded to linear light and drawn on the inside of a sphere whose fragment shader derives right ascension and declination from each pixel's own view direction rather than trusting sphere texture coordinates, so it lines up with the plotted stars by construction. A single intensity uniform scales it; the interface slider's 0–100% maps onto 0–0.3 linear, with the default at 17%.

1.6What this enables next

The satellite layer has a place waiting for it: the world group, in the inertial frame the propagator works in, with GMST already computed by the same formula the propagator library uses. A Web Worker will run SGP4 over every element set about once a second and post positions and velocities in a typed array; the main thread will extrapolate between updates and draw one point cloud beside the Earth, with an orbit path for whatever is selected. Nothing in the globe needs to change for that to happen.

The pipeline pattern is proven: a raw upstream file, a module that validates and reshapes it, a small column-oriented file the browser turns straight into GPU attributes. The satellite snapshot — element sets plus catalogue metadata, refreshed every two hours under CelesTrak's one-download rule — is the next module in that pattern, and the daily archive it will keep is the foundation of every history feature the plan describes.

And the asset weights measured here are exactly what a static host would serve. Nothing stands between the current build and a public URL except the decision to put it there.

The Orbit Pipeline

11 September 2026 · commit a0ba44a · pipeline/ap_pipeline/orbits, pipeline/scheduling, web/vite.config.ts, data/{orbits,raw,archive,logs}

2.1Context

The globe was ready to receive satellites; what it lacked was the element sets to place them with. Part 1 had already rehearsed the pattern — a raw upstream file, a module that validates and reshapes it, a small file the browser reads — on data that never changes. Orbital elements change every two hours, come from a source with strict usage rules, and are worthless if they are stale or wrong. The pipeline for them therefore had to be three things the texture and star modules never needed to be: scheduled, well-behaved toward its source, and suspicious of its own input.

The source rule shaped everything. Since 26 March 2026 CelesTrak permits one download per dataset per two-hour update window; a second request in the same window is answered with HTTP 403, and repeated abuse with a block. The rule is reasonable — the data is derived from the 18th Space Defense Squadron's catalogue and served free — and it makes a naive "fetch on a timer" pipeline a liability rather than a convenience. Jack's brief for this stage was one sentence: downloading the satellite data, with a pipeline for regular scheduled downloads, data storage and validation. We read "regular" as "hourly, safely", and built the client so that running it too often is harmless by construction.

We also decided, before writing any client code, to look. One small request — the ISS by catalogue number, a dataset we never use — showed exactly what CelesTrak sends back: JSON with 17 OMM fields, no Last-Modified, no ETag. That single fact changed the design from conditional HTTP requests, which the server cannot honour, to time-based pacing, which it can. The request cost one window on a dataset we do not fetch, and it saved a wrong design.

2.2What was built

Five modules and a scheduler script. The pipeline gained a package, ap_pipeline/orbits, with one module per concern, each named for what it does: celestrak_client (the well-behaved HTTP client, its gates and its memory), validate_element_sets (shape and range checks, propagator initialisation, propagation, de-duplication, flags, derived orbit numbers), satcat (the satellite catalogue as a lookup by catalogue number), build_orbit_snapshot (validation plus catalogue join, written as the file the site loads) and run_orbit_update, the single entry point the scheduler calls. Beside it, pipeline/scheduling/register_windows_task.ps1 registers, inspects or removes the hourly job. Two new dependencies arrived with them: httpx for HTTP and sgp4, Brandon Rhodes' Python binding of the reference SGP4 implementation.

Seven datasets. Six CelesTrak GP groups — active (every active satellite, 16,564 objects), stations, last-30-days (recent launches not yet flagged active), and the Fengyun-1C, Iridium 33 and Cosmos 2251 fragmentation clouds — plus the SATCAT, the 70,656-row catalogue that gives each object its type, owner, launch date and site, operational status and radar cross-section class. CelesTrak publishes no all-objects group; the remaining ~16,000 tracked rocket bodies and fragments live only in Space-Track's catalogue, which needs an account and, for public redistribution, an Orbital Data Request. That decision was left to Jack and is still open; the six groups cover every active satellite and the three largest debris clouds.

Storage with the production shape. Under the git-ignored data/: every raw response, untouched, for seven days; the client's memory in orbits/state.json; the current snapshot and its manifest in orbits/latest/; one gzipped copy of each dataset per UTC day in archive/, kept forever; and a log with UTC timestamps. A forty-line middleware in the Vite configuration serves orbits/latest/ at /data/orbits/ with the exact cache headers object storage will send later — the manifest always revalidated, the versioned snapshot immutable for a year — so the browser side could be written once against the real contract.

The scheduled job. Windows Task Scheduler, hourly at seventeen minutes past, only when the network is available, twenty-minute time limit, no overlapping instances. The task is deliberately dumb; the pipeline decides internally whether anything may be fetched. Registered with Jack's approval and exercised by hand: exit 0, nothing fetched, gates held. Its first unattended fetch came at 21:17 UTC that evening and produced a new snapshot without anyone watching.

2.3How it works

The gates. On every run the client considers each dataset in turn and asks four questions before it will make a request (Figure 2.1). Is the whole client backing off after a server error? Has this dataset's next-allowed time not yet arrived? Was it asked for less than 58 minutes ago? Was it successfully downloaded less than 1 hour 50 minutes ago? A yes to any of them means no request. Only when all four are no does a GET go out, with a User-Agent that names the project and a contact address, as the policy asks.

Each answer then updates the memory. A 200 stores the body untouched in data/raw, hashes it to learn whether the content actually changed, and sets the next-allowed time 1 hour 50 minutes ahead. A 403 means we asked before CelesTrak's own update landed; it is recorded as information, not failure — the old file stays current and the dataset may be asked for again in 58 minutes. A 5xx stops the entire run and blocks every dataset for six hours, because a struggling server is the one thing a polite client must not add load to. A 301 or a 404 raises an error and exits with code 2, because a moved or vanished endpoint is a change only a person should respond to.

Locking onto their cadence. CelesTrak updates on a two-hourly phase we cannot see. Our first request in a window succeeds at some offset after their update; if we then ask every two hours at the same minute, that offset never changes and we never see a 403. If we happen to ask just before an update, that request gets a 403, the next hourly run succeeds, and the offset becomes roughly an hour — stable from then on. We expect one or two 403s in the pipeline's whole life, both harmless. The state file is the client's memory of all this: per dataset, the last attempt, last success, last status, the newest raw file's path and SHA-256, the next-allowed time and a count of consecutive 403s; globally, the back-off time and when the SATCAT directory was last checked. Deleting it is the one way to make the client misbehave, and it says so in a comment inside.

The SATCAT is cheaper. CelesTrak's directory listing for it (satcat/jsonDir.php) does report a modification time. The client polls that listing at most hourly and downloads the 70,656-row CSV only when the time has changed, which is once or twice a day.

Three layers of validation. Nothing reaches the snapshot without passing all three, each catching what the previous one cannot. First, shape and range: thirteen required fields present and numeric, eccentricity in [0, 1), inclination in [0°, 180°], mean motion in (0, 20] revolutions per day, an epoch that parses; then de-duplication — the six groups overlap (the ISS is in active and stations), and for each catalogue number the newest epoch wins. Second, initialisation: the sgp4 package's OMM loader builds a propagator record from the exact field names CelesTrak sends, and anything it refuses is rejected with the exception's name as the reason. Third, propagation: every accepted record is propagated, vectorised, at three moments — its own epoch, now, and now plus one day — and SGP4's own error codes speak: 6 means the object has decayed, 5 sub-orbital, 1–4 numerical pathologies a range check cannot see. Sets older than fourteen days are kept but flagged stale; older than sixty days they are dropped. The validator also derives, from the elements alone, each object's period, semi-major axis, apogee and perigee altitudes and a coarse regime — LEO, MEO, GEO, HEO or beyond — so the site's first filters need no further arithmetic.

The snapshot and the manifest. The snapshot is column-oriented: a columns block describing each of 32 fields, and a data block holding one array per field, all of the same length, sorted by catalogue number. The 17 OMM fields are carried verbatim — the epoch as CelesTrak's ISO string, the numbers as the same doubles — so the browser can rebuild any object's OMM record and hand it to its propagator unchanged; the derived orbit numbers, the flags, the groups an object appeared in, and seven SATCAT fields ride alongside. The manifest is what the site reads first: the current version, the snapshot's filename and size, the counts by type and regime and group, the validation summary, and provenance for every input. Its name never changes and it is served no-cache; the snapshot's name carries its version and is served immutable, and the newest two versions are kept so a page that has already read the manifest can still fetch its file during a rebuild.

One run, start to finish. Load the state; for each group, pass the gates or skip; check the SATCAT listing; if anything new arrived (or no snapshot exists yet), validate everything and write a new snapshot and manifest; write today's gzipped copy of every dataset into the archive; delete raw files older than seven days; write a summary of the run and append to the log; exit 0, or 2 if the run was halted. A run in which every gate says skip takes a third of a second. The archive keeps each day's last state — overwritten within the day, final at midnight — about 2.8 MB a day, a gigabyte a year, and the raw material for every "how did this orbit change" feature in the plan.

The Satellite Layer

11–12 September 2026 · commits 2749616, 05b5893 · web/src/lib/orbits, web/src/lib/globe/{satellites,orbitPath}.ts, web/src/lib/astro/frames.ts, web/src/lib/state/catalog.svelte.ts, web/src/ui

3.1Context

This is the part the project exists for. Part 1 built a world with a coordinate frame and a clock; Part 2 built a supply of element sets that arrives every two hours in a form the browser can trust. What remained was to put 19,247 objects into that world, moving, at the right places, at any speed of time the clock can run, with the page still rendering at the refresh rate of the display — and to do it in a way that leaves the main thread nearly idle, because everything the plan describes after this (search, passes, explorers) will want that idle time.

Jack's brief was a sentence and two questions: plot the satellites into our system, make it look visually impressive and clean, and let me know the load times and what is required of the browser versus my local machine. The second question is a design constraint disguised as a request for a report: the split between what his PC does on a schedule and what every visitor's browser does on arrival is the architecture. The answer is in 3.3 and the numbers are in 3.5.

Two things were true before a line was written. The game plan had already decided on satellite.js — a JavaScript port of the reference SGP4/SDP4 implementation — running in a Web Worker, with the main thread extrapolating between its updates. And the snapshot from Part 2 carries every element set verbatim under its OMM names, so satellite.js's OMM loader could be fed the columns directly. What the plan had not decided was how many workers, how often they should run, and how far the extrapolation could be trusted. Those were measured before they were designed.

3.2What was built

A benchmark first. Before any browser code, we ran satellite.js 7 in Node against the real snapshot. Building 19,247 propagator records took about 100 ms. Propagating all of them at one instant took 54 ms on the first call and 7–10 ms once the JavaScript engine had warmed; the library's WebAssembly bulk propagator took 5 ms; its four-thread build took 11–14 ms, slower than one thread, because the synchronisation costs more than it saves at this size. The JavaScript and WebAssembly paths agreed to a micrometre. Those five numbers settled the architecture in an hour: one worker, plain JavaScript, no worker pool, no cross-origin-isolation headers, and a tick rate of up to thirty per second with room to spare.

The loader and the catalogue. loadOrbitSnapshot makes the two requests Part 2 designed for — the manifest, always revalidated, then the immutable versioned file it names — streaming the second so the status bar can show bytes arriving, then parsing and checking the 17 OMM columns. SatelliteCatalog is a read-only view over the parsed columns with one byte per object for type, regime, debris-cloud membership and staleness, counts by class, a map from catalogue number to index, and the filter mask the GPU reads. It contains no Three.js and no Svelte, so the interface, the globe and the propagation engine share it freely.

The worker and the engine. propagation.worker.ts receives the OMM columns, builds one satellite.js record per object, and on request runs SGP4 for every object at one simulation instant, writing position and velocity into two transferable buffers that cross to the main thread without copying and come back for reuse. It also samples one revolution of any object on demand. PropagationEngine is the main-thread half: it owns the worker, decides when to ask (3.3), keeps at most one request in flight, measures the round trip, and hands finished frames to the layer.

The layer. SatelliteLayer is one Three.js Points object with a custom shader pair. The vertex shader moves each point along its velocity with point-mass gravity, colours it by type or regime, dims it inside the Earth's shadow, scales it by its distance from the camera, and enlarges the hovered and selected object; the fragment shader draws an anti-aliased disc with a dark rim so a dot reads over black space and sunlit cloud alike. The layer is depth-tested against the Earth, so the far side of the shell is hidden. Beside it, OrbitPath draws one revolution of the selected object as a closed line that is brightest at the object and fades toward the far side of the orbit, its bright end following the object by a phase uniform rather than by recomputation.

Interaction and interface. Hovering names an object — name, catalogue number, type, regime, perigee and apogee — in a label at the pointer. A click selects it, draws its orbit, and opens a card: live latitude, longitude, height above the WGS84 ellipsoid, speed, sunlit or eclipsed; then period, perigee and apogee, inclination, eccentricity and the element set's epoch and age; then owner, launch date and site, operational status and radar size, with the SATCAT codes spelled out. The Layers panel gained a Satellites section: the active catalogue and the debris clouds as separate toggles (active on by default, as decided in the plan), colour by type or by regime with a legend and counts, a size slider, Earth's shadow, and the orbit line. The status bar reports how many objects are shown, how old the snapshot is, the worker's tick rate and time per tick, and the load timeline. Picking is done on the CPU with the same extrapolation the shader draws, so what the pointer hits is exactly what is on screen.

Live refresh. The page re-reads the manifest every ten minutes and whenever its tab regains focus; when the pipeline has published a new version, the page loads it in the background, builds a new layer and worker, swaps them in, and keeps the selection by catalogue number. The test was real: a snapshot rebuilt by hand while the page was open was picked up and swapped in with the ISS still selected.

The review, folded in. Jack's first look on his own display produced four notes within the hour. The points were the right size at 15,000 km but too small when he flew in close: fixed-pixel sizing became depth scaling. Two lines of satellites appeared at constant latitudes when time ran at 3,600× — near Glasgow and just above the Alps — and he wanted to know whether they were real (they are; 3.5 has the numbers). The card's "Perigee · apogee" label wrapped and threw the row out of line: labels no longer wrap. And, with sixteen thousand white dots over the planet, the stars were invisible and indistinguishable, and the Milky Way map "very poor resolution". The palette lost its white: payloads became cyan, debris lavender, rocket bodies amber, so stars and satellites can never be confused. The Milky Way we regenerated at twice the resolution with a third of the blur (Part 1 describes the original); the result was sharper but grainy — a count of 2.5 million stars is a sparse sample of the galaxy, and at that resolution the grain is the stars themselves. Jack chose removal over a photograph, and the map, its shader, its slider and its builder were deleted the next morning. His status-bar reading of 36 Hz at 3,600× also exposed a real bug in the engine — 3.3 explains it — which was fixed before the stage was committed.

3.3How it works

Three actors, three kinds of memory. The pipeline wrote the snapshot hours ago. The main thread fetches it once and keeps the human-readable columns — names, owners, periods — for the interface. The worker keeps the propagator's own records and does all the orbital arithmetic. The GPU keeps two small buffers of positions and velocities and does the per-frame motion itself. Element sets cross the worker boundary once, at load; afterwards only positions and velocities move, by transfer, and the GPU carries them between ticks (Figure 3.1).

Why the shader moves the points. Running SGP4 every frame would cost 7–10 ms of main-thread time per frame — most of a 60 Hz budget and more than a 240 Hz frame has. Instead the worker computes exact positions p₀ and velocities v₀ at one instant t₀, and the vertex shader, which runs on every vertex every frame anyway, draws each point at p = p₀ + v₀Δt + ½aΔt², with the acceleration a = −μp₀/|p₀|³ computed from the point's own position — point-mass gravity, μ = 398,600.4418 km³/s². Between ticks a satellite is therefore on a parabola tangent to its orbit. The residual grows with the cube of Δt: for a 400 km orbit, where the acceleration turns at about 0.01 m/s³, one second of extrapolation is wrong by a fraction of a millimetre and sixty seconds by about 350 m. The main thread's whole per-frame contribution is one number, Δt.

The timing model. The engine ties two clocks together — real seconds, which limit how often the worker can finish, and simulation seconds, which the shader must bridge — with three rules. Ticks are spaced 1000 ms divided by the time rate, clamped between 33 ms and 1000 ms: one a second at real time, thirty a second from 30× upward, none while paused. A new request is never sent while one is unanswered, so a slow machine ticks less often rather than queueing up. And each request asks for positions not at "now" but at now + rate × (round trip + interval ÷ 2) — the simulation instant halfway through the time the answer will be on screen — so the shader extrapolates half an interval backward and then half forward, and the worst-case Δt is halved for free. At 3,600× that means ±60 simulated seconds and roughly 350 m of error for the lowest orbits, which is a fraction of a pixel at globe scale.

A jump — the user picking a date — is detected by comparing where the clock is with where the last request predicted it would be. The first version used a fixed tolerance of 1.5 simulated seconds, which at 3,600× is only 0.4 ms of real time: ordinary frame jitter tripped it, and the engine fired extra ticks. Jack's status bar read 36 Hz against a 30 Hz cap, which is how the bug was found; the tolerance is now the larger of 1.5 s and sixty real milliseconds scaled by the rate.

Frames and shadow. The layer is a child of the world group in the Earth-centred inertial frame, exactly as Part 1 reserved. In the inertial view the group is fixed and the Earth rotates inside the shell of points; in the Earth-fixed view the group turns by −GMST and everything stays consistent with no per-object work. The worker emits positions already in the scene's axis order — the propagator's (x, y, z) as (x, z, −y) — so its buffers go straight to the GPU. Earth's shadow is a cylinder test in the vertex shader against the same world-rotated sun vector the Earth shader receives: an object behind the planet and within one Earth radius of the anti-sun axis is dimmed to 30% and cooled toward blue, with a soft edge of about 150 km.

Picking and the readout. Hover picking runs at most 25 times a second while the pointer moves. It evaluates the same extrapolation on the CPU for every visible object, projects each through the camera, ignores anything whose line of sight passes through the Earth, and takes the nearest within nine pixels (twelve for a click; a press that travels more than five pixels is a drag, not a click). The card's live numbers come from the same sample: scene position back to ECI, ECI to Earth-fixed by GMST, then the iterative WGS84 conversion to geodetic latitude, longitude and height — the proper ellipsoidal conversion, added to frames.ts in this part, converging to double precision in four rounds.

Depth scaling. After review, a point's size is its base size (3.4 px for payloads, 2.5 for debris) times (17,000 km ÷ view depth)^0.6, clamped between 0.6 and 4. True perspective (exponent 1) makes the near side of the shell ten times the far side; 0.6 grows the dots as the camera approaches without that imbalance, and tapers the shell far out instead of letting it fuse into a solid ring.

The two lines deserve their explanation, since the measurement is the answer. 4.1Context

Part 3 ended with nineteen thousand dots moving correctly and a promise: the catalogue is in memory, indexed and cheap to walk, so everything that follows is interface. This part cashed the first of those promises. A globe of every object in orbit is impressive for about a minute; after that a visitor wants to find the one they came for — the station, the telescope, the constellation that has been in the news — and to see it against the rest. Jack's direction was to add search and constellations first and then to think about what else a visitor might do; this part is the first half of that sentence.

Two constraints shaped it. Nothing new was to be fetched, computed by the pipeline, or added as a dependency: the columns already parsed on the main thread had to be enough. And the result had to be shareable, because the address bar is the cheapest possible interface for "look at this".

4.2What was built

Rules from the data, not from memory. Before writing a constellation rule we counted name prefixes and owner codes in the live snapshot. That is how China's Guowang turned up as HULIANWANG (191 objects) and Geely's fleet as GEESAT (63), and why the IRIDIUM and FENGYUN rules match payloads only — otherwise the Iridium 33 and Fengyun-1C debris clouds would have been folded into the fleets they came from. The result is a table of 43 rules in six categories: broadband megaconstellations, communications and IoT, navigation, Earth observation and weather, stations and recent launches, debris clouds. A rule is either a pattern on the catalogue name or a reference to one of the pipeline's groups. 16,544 of the 19,246 objects fall into a rule; the rest are one-off payloads, rocket bodies and unknowns, and the count beside each rule in the panel is its audit.

Search. A box in the top bar, focused by / from anywhere on the page. Each keystroke scans every name; results are ranked and capped at forty; ↑↓ Enter Esc do what they should; the empty box offers examples. Because CelesTrak's names are not the ones people use, an alias table maps "Hubble" to HST, "Tiangong" to the three CSS modules, and a handful of others — the first search for Hubble had returned nothing, which is how the table came to exist.

Groups. A panel beside Layers: the six categories as rows with operator and count; the fourteen largest owners by SATCAT code with their names spelled out; chips for payload, rocket body, debris and unknown. Picking a group and an owner combine. A picked set is described in place — objects, and how many launched in the last thirty days; types; regimes; median perigee and apogee; the five most populated inclination bins in half-degree steps; first and latest launch dates; top owners — which is how a visitor learns that Starlink is 11,129 objects in four shells at 53°, 43°, 97.5° and 70°, or that GPS is forty satellites between 19,913 and 20,467 km flown since 1997.

Two ways to recede. Dim, the default, keeps the rest of the catalogue on screen at ten percent alpha and seventy percent size, so a group reads against its context; Hide removes it, so the group can be studied alone and the status bar's count becomes the group's. Hovering and clicking ignore dimmed objects.

Fly-to and links. Choosing an object from search, from a link, or with the card's Locate button swings the camera round to it over 900 ms; the card also shows the object's group as a chip that picks it out. The address bar follows the selection and the pick — ?sat=25544&group=stations — and a link opens the site on that object, flying to it once the catalogue has loaded.

4.3How it works

One integer per object. When a snapshot loads, every object is tested against the rules in order and given the index of the first that matches, or −1: an Int16 per object, computed once. From then on a pick is two byte-per-object masks — membership, and the existing visibility mask — recomputed in about a millisecond whenever a setting changes, and the GPU does the rest (Figure 4.1).

Search. The query is upper-cased, whitespace-collapsed and passed through the alias table. Every object's name is tested once; a numeric query is compared against the catalogue number first. Each hit gets a rank — exact number, name starts with, designator starts with, name contains, number starts with — and multi-word queries require every word. The first forty are taken bucket by bucket in catalogue order, which is launch order, so "STARLINK" lists the oldest Starlinks rather than a random forty, and only those forty are sorted by name for display. The total is reported alongside so the footer can say "first 40 of 11,129". The whole thing is a linear scan: under two milliseconds for nineteen thousand names, which is why there is no index.

Dimming as an attribute. The shader from Part 3 gained one byte per point, aEmphasis, and one uniform that says whether a pick is active. Non-members are drawn at ten percent alpha and seventy percent size by the vertex shader; nothing is re-uploaded but that one byte array, and the per-frame cost is zero. Hide instead ANDs the membership into the visibility mask, and hidden points are moved outside clip space as before. Picking reads both masks, so a dot you can barely see cannot be hovered.

The flight. A flight stores the camera's starting direction and the target's index. Every frame it re-reads the target's current position — the same extrapolation the shader draws — eases a blend from 0 to 1 over 900 ms, interpolates between the two unit directions, and places the camera along the result at its original distance, looking at the Earth's centre. Because the direction is re-read each frame the camera lands on a moving satellite, not where it was when the flight began. A drag cancels it; a request that arrives before the first positions waits for them instead of giving up, which is what a link opened cold needs.

The address bar. Selection and pick are written with replaceState, so the back button leaves the site rather than stepping through satellites; on load the parameters are applied once the catalogue is ready. Links carry catalogue numbers, which are stable across snapshots, and group identifiers, which are ours.
