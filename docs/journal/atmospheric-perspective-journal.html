Preface

Atmospheric Perspective is a browser-based platform for satellite data. Its centrepiece is a three-dimensional globe on which every publicly tracked object in Earth orbit will move in real time, propagated in the browser from fresh orbital element sets; around it sit explorers, dashboards and observer tools built on the same data. The project is deliberately static-first: the browser does the orbital mechanics, a small pipeline refreshes the data on a schedule, and hosting is meant to cost nothing. A previous version of this idea, built on a cloud provider with orchestration and containers added early, taught the lesson that shapes every decision here: add machinery only when a feature demands it.

This journal is written as the work happens. Each part covers one component of the system and follows the same six headings — context, what was built, how it works, decisions and alternatives, measurements, what this enables next — so that the document reads as one process from the first line to the last. Where a component was revised after review, the revision is told inside the same part rather than as a separate chapter, because the revision is part of how the thing came to be.

The Globe

11 September 2026 · commits 7a3e84d, f16d9b8 · web/src/lib/{astro,globe,state}, web/src/ui, pipeline/ap_pipeline/{textures,sky}

1.1Context

Before any satellite could be drawn, the world it would be drawn into had to exist: a planet with the correct shape, lit by the real Sun for the real time, turning at the right rate under a sky fixed to the stars. Everything a satellite layer will need — a coordinate frame, a clock, a way to turn simulation time into a picture — is decided here, and the cheapest time to decide it correctly is before there are ten thousand moving objects depending on it.

The plan that preceded the build (the "game plan", 11 September 2026) had already fixed the architecture: a Svelte 5 single-page application built with Vite, rendering through Three.js with hand-written shaders, and a Python pipeline that turns raw upstream data into small static files. It had also surfaced one fact that made the static-first design mandatory rather than merely economical: since 26 March 2026 CelesTrak, the public source of orbital element sets, permits one download per dataset per two-hour update window and answers a second with HTTP 403. A site whose browsers fetched element sets directly would fail on its second visitor. The pipeline therefore fetches once and the site serves its own copy — and that same pattern, raw data in, small derived file out, was rehearsed in this part with the sky before it is trusted with the satellites.

The work was done in two sittings on the same day. The first produced a working globe from nothing; Jack reviewed it and asked for four things — slower camera drag, a sharper Earth, a fuller sky "possibly even the centre of the Milky Way, though I like the idea of plotting the stars rather than an image", and the Sun visible in its true position — plus a subtle cloud layer and more descriptive file names. The second sitting delivered those. This part describes the result as one thing, and notes along the way what the first pass did differently and why it changed.

1.2What was built

The toolchain. We installed Node.js 24.19 (for the build tools only; nothing of ours runs on Node in production) and later uv 0.12 for the Python side. Python 3.14 and Git were already present. The web application is Svelte 5.57, Vite 8.3, TypeScript 5.9 and Three.js r186; the production build is a single HTML file, one stylesheet and one 165 KB (gzipped) script, Three.js included.

The repository. A monorepo with three concerns — web/ for the site, pipeline/ for the data work, docs/ for briefs and this journal — plus a git-ignored data/raw/ for downloaded originals. Inside web/src the dependency direction is strict and one-way: user interface → shared state → globe → astronomy. The astronomy modules import nothing but a vector type; the globe modules never import Svelte; the interface never touches Three.js except through one component, GlobeCanvas, which is the deliberate bridge.

The Earth. A WGS84 ellipsoid — equatorial radius 6378.137 km, polar 6356.752 km — textured with NASA's Blue Marble Next Generation (December 2004, with topography and bathymetry) by day and Black Marble 2016 city lights by night. The first pass used NASA's 5400×2700 JPEG directly. On review it was judged too soft, and we went back to the 21,600×10,800 original (30 MB) and had the pipeline resample it to three WebP tiers of 2048, 4096 and 8192 pixels wide; the site paints the 2048 tier within about a second and swaps the 8192 tier in behind it. A custom fragment shader blends day and night across a soft terminator, adds Lambert shading, warms the light near the terminator, glints off water and tints the disc blue toward the limb.

The atmosphere. A shell 4.5% larger than the Earth, drawn back-face only with additive blending. Because the Earth is drawn first, only the ring of shell outside the planet's disc survives the depth test, and that ring is the glow — brightest at the limb, fading outward, dimmer on the night side, warmer near the terminator.

The clouds. Added in the second sitting: NASA's Blue Marble cloud composite as a translucent shell 25 km above the surface, opacity 0.42, lit by the same sun vector as the ground so it shares the terminator. Clouds also darken the ground beneath them by up to 22% and hide up to 80% of the city lights below, which is what makes the shell read as a layer rather than paint. The sheet drifts eastward at 0.25° per simulated hour — an artistic touch, invisible at real speed, documented as non-physical.

The Sun. A billboard sprite placed along the computed sun vector each frame, drawn with a canvas-generated radial gradient whose inner stop is sized so the bright disc subtends the Sun's true 0.53°, inside a soft nine-degree glare. It is drawn in the sky pass, so the Earth occludes it: sunrise and sunset over the limb need no special handling.

The stars. The first pass plotted the Yale Bright Star Catalogue — 9,096 naked-eye stars — as points. It looked sparse. The second pass replaced it with the HYG database (Hipparcos, Yale and Gliese combined): 119,613 stars, each at its J2000 right ascension and declination in the inertial frame, sized and faded by visual magnitude and coloured by its B−V index through a small black-body ramp. Because the stars live in the inertial frame they hold still while the Earth turns beneath them, which is what the sky does.

The Milky Way. Jack's brief was specific: see the galaxy, but plot data rather than paste a photograph. The galaxy, to the eye, is the integrated light of stars too faint to resolve individually, so we reproduced it the same way. The pipeline reads the Tycho-2 catalogue — 2,539,913 stars — sums their light into a sky-brightness map, and the browser drapes that map over the celestial sphere underneath the plotted stars. The band, the dark lanes of the Great Rift and the bulge toward Sagittarius all emerge from the catalogue. The map is 4096×2048 pixels and 202 KB.

Time and frames. A simulation clock that follows the wall clock, or runs at 1× to 3,600× real time, or pauses, or jumps to a chosen date; every visible quantity is recomputed from its single value each frame. Two reference frames, switchable without a visual jump: inertial (the sky holds still, the Earth turns) and Earth-fixed (the Earth holds still, the sky and Sun move).

The interface. A top bar with the wordmark, a live UTC clock and a LIVE / SIM / PAUSED badge, the frame toggle and a Layers button; a layers panel with toggles for day/night shading, city lights, clouds, atmosphere, stars, the Milky Way and a 15° graticule, plus sliders for star brightness and Milky Way intensity; time controls; and a status readout of camera latitude, longitude and altitude, the sub-solar point, sidereal time, frame rate, texture tier and star count, with data credits beneath.

The pipeline. Three Python modules, named for what they do, run from a uv project with two dependencies (NumPy, Pillow): build_earth_textures_from_nasa, build_star_catalog_from_hyg, build_milky_way_glow_from_tycho2. The first pass had a single dependency-free script called build_stars.py; the name was rightly called out as saying nothing, and the restructuring followed.

1.3How it works

Coordinates. Scene units are kilometres. The scene is laid out in the Earth-centred inertial frame — x toward the vernal equinox, z toward the north pole — remapped to Three.js's y-up convention as scene.x = eci.x, scene.y = eci.z, scene.z = −eci.y. The mapping is right-handed, puts north up, and makes east longitude increase in exactly the direction an equirectangular texture wraps onto Three's sphere, so the Earth needs no texture offset: rotating the mesh by Greenwich Mean Sidereal Time about y puts Greenwich where it belongs. GMST is computed from the Julian date with the same polynomial the satellite propagator library uses, so the Earth and the future satellites will agree on where Greenwich is.

The scene graph. Two groups do the work. earthGroup holds the Earth mesh, the cloud shell, the atmosphere shell and the graticule; it is scaled by 6356.752/6378.137 in y so the whole planet is an ellipsoid, and it rotates by GMST every frame. Its parent, world, is the inertial frame, with rotation zero in the inertial view. Switching to the Earth-fixed view sets world's rotation to −GMST, which exactly cancels the Earth's spin, and rotates the camera by the same delta at that instant so the picture is continuous. Satellites will be children of world, because that is the frame their propagator produces.

The sky is a second scene rendered first, through a camera that copies the main camera's rotation but never its position, so the stars are at infinity regardless of zoom and never touch the depth buffer. Its root group carries the Milky Way dome, the star points and the Sun sprite in that draw order, and follows world's rotation so the sky and the Earth stay consistent in both frames. The depth buffer is cleared between the two passes; the Earth therefore always occludes the sky — and the Sun — behind it.

One frame. The browser asks for a frame roughly sixty times a second (240 on Jack's machine). Each time, the globe asks the clock for the simulation time, converts it to a Julian date, computes GMST and the Sun's direction (the Astronomical Almanac's low-precision solar algorithm, accurate to about a hundredth of a degree), poses the two groups, writes the sun vector and camera position into the shader uniforms, renders the sky and then the world, and every 200 ms reports a status object back to the interface. The interface, for its part, pushes changes into the globe through Svelte effects — a frame toggle, a layer switch, a slider — and otherwise leaves it alone.

Lighting without lights. There are no Three.js light objects. Every shader receives the same sun vector and computes dot(normal, sun) per pixel. On the Earth a smoothstep over ±0.10 in that quantity gives a twilight band roughly twelve degrees wide; the day side gets Lambert shading plus a warm push toward the terminator, a specular glint where the Blue Marble is blue, and a blue tint toward the limb; the night side shows 3.5% of the day texture plus the city lights tinted sodium-orange. The cloud shader lights coverage the same way, warms it near the terminator and dims it to blue-grey at night. The Earth shader also samples the cloud map, offset by the same drift, to shadow the ground and dim the lights beneath cloud.

Two loading tiers. The globe loads in two waves. Wave one fetches the 2048-wide day, night and cloud maps, the star binary and the Milky Way map in parallel — about two megabytes — builds every object, and reports ready. Wave two fetches the 8192 day and night maps and the 4096 cloud map, hands them to the shells, and frees the small ones; nothing on screen changes except sharpness. A returning visitor loads all of it from cache.

The pipeline, module by module. Each module reads originals from data/raw/ and writes something small into web/public/. The texture module opens the 233-megapixel Blue Marble (Pillow's decompression-bomb guard has to be switched off), converts to RGB and resamples with a Lanczos filter to each tier, saving WebP at quality 86; the same for Black Marble and, as a single grey channel, the cloud composite. The star module reads the HYG CSV, converts right ascension from hours to degrees, drops the Sun, sorts by magnitude and packs each star into four little-endian 16-bit integers — RA and Dec in hundredths of a degree, magnitude and B−V ×100 — eight bytes a star, a precision of 36 arcseconds, thirty times finer than a screen pixel at the globe's field of view; names for 759 stars go in a sidecar file keyed by row.

The Milky Way module is the one worth describing in full. It reads all twenty Tycho-2 parts (four seconds in Python 3.14), converts each star's Tycho BT and VT magnitudes to Johnson V and B−V with the standard relations, and discards stars brighter than V 8, which are plotted individually and would otherwise be counted twice. Each remaining star contributes a weight of 10−0.4·max(V, 10) — flux, but capped at tenth magnitude, so a single ninth-magnitude star cannot make a blob and the map traces the density of faint stars, which is the classic technique for Tycho-2 all-sky maps and is what the eye actually perceives. Contributions are coloured by B−V through the same black-body ramp the browser uses, binned into a 4096×2048 grid of right ascension and declination, and divided by the cosine of declination so that a pixel near the pole, which covers less sky, is expressed as surface brightness rather than count. The grid is then smoothed with a Gaussian of seven pixels (about 0.6°) by FFT, chosen because it wraps at RA 0° and leaves no seam; the 55th-percentile floor is subtracted so empty sky is black, the result is normalised to the 99.8th percentile and given a gamma of 0.85, and the map is written as WebP.

In the browser the map is decoded to linear light and drawn on the inside of a sphere whose fragment shader derives right ascension and declination from each pixel's own view direction rather than trusting sphere texture coordinates, so it lines up with the plotted stars by construction. A single intensity uniform scales it; the interface slider's 0–100% maps onto 0–0.3 linear, with the default at 17%.

Two things we could not measure well deserve saying. The frame rate cannot be read in the embedded browser pane, which pauses animation when it is not displayed; the 240 fps figure is Jack's reading of the first pass on his own display, and the second pass — two more full-screen shells and thirteen times the star points — is awaiting his. And the star brightness, Milky Way intensity and cloud opacity were calibrated from downscaled captures; the sliders exist so that the defaults can be set from a full-resolution view and then baked in.

1.6What this enables next

The satellite layer has a place waiting for it: the world group, in the inertial frame the propagator works in, with GMST already computed by the same formula the propagator library uses. A Web Worker will run SGP4 over every element set about once a second and post positions and velocities in a typed array; the main thread will extrapolate between updates and draw one point cloud beside the Earth, with an orbit path for whatever is selected. Nothing in the globe needs to change for that to happen.

The pipeline pattern is proven: a raw upstream file, a module that validates and reshapes it, a small column-oriented file the browser turns straight into GPU attributes. The satellite snapshot — element sets plus catalogue metadata, refreshed every two hours under CelesTrak's one-download rule — is the next module in that pattern, and the daily archive it will keep is the foundation of every history feature the plan describes.

And the asset weights measured here are exactly what a static host would serve. Nothing stands between the current build and a public URL except the decision to put it there.
